### 2. 下午:改成"一次写 32 位" ✅

```c
// 改之前:逐字节写 4 次
uint8 *Pixel = (uint8 *)Row;
*Pixel++ = Blue;  *Pixel++ = Green;  *Pixel++ = 0;  *Pixel++ = 0;

// 改之后:拼成 1 个 32 位值,一次写进去
uint32 *Pixel = (uint32 *)Row;
uint8 Blue  = (uint8)(X + Xoffset);
uint8 Green = (uint8)(Y + Yoffset);
*Pixel++ = ((uint32)Green << 8) | (uint32)Blue;
```

**实测(本机微基准,1280×655,50 帧)**:

| 编译参数 | 逐字节写(4 次) | 一次写 32 位(1 次) | 倍数 |
|---|---|---|---|
| **`-Od`**(和 `build.bat` 一样不优化) | 2.494 ms/帧 | **1.063 ms/帧** | **2.35×** |
| **`-O2`**(开优化) | 0.513 ms/帧 | **0.420 ms/帧** | **1.22×** |

结论:**别指望编译器兜底** —— Release 下它确实合并了大部分,但没全合并(还差 22%);而 Debug 构建(`-Od`,我们的 `build.bat` 就是)**完全不合**。

**为什么值得这么写(四个原因)**:① 内存写次数少 4 倍(336 万 → 84 万次/帧);② 指针算术少 3/4;③ 用 `uint32*` 等于告诉编译器"我按 4 字节对齐访问";④ 别指望编译器兜底(见上表)。
**边界**:必须 32bpp(24bpp 会导致大量未对齐访问,甚至写坏相邻像素);对齐的 32 位写对其他 CPU 核是**原子**的。

## 六、今天搞懂的概念

| 概念 | 一句话 |
|---|---|
| **一次 32 位写 vs 逐字节写** | 一个像素 = 一个 32 位值;写 1 次比写 4 次快,指针也只自增 1 次 |
| **编译器的"自动合并"是有限的** | Debug(`-Od`)完全不合;Release(`-O2`)合了大半但没全合(还差 22%) |
| **对齐访问** | 一次 32 位存储要求地址是 4 的倍数,否则踩 CPU 惩罚;32bpp 让"宽 × 4"天然对齐 |
| **`uint8` 溢出回绕 → 彩虹条纹** | 每 256 个像素颜色绕一轮,所以屏幕是一道一道的彩条,不是一条顺滑渐变 |
| **指针 `++` 前进多少由类型决定** | `uint32*` 的 `++` = 前进 4 字节(正好一个像素),`uint8*` 只前进 1 字节 |
| **`\|` vs `+` 合并位段** | 两段位不重叠时结果相同;`+` 一旦写错会**进位污染**旁边那段,`\|` 只会"盖上去" |
| **注释不是理解** | 今天给每个变量都写了注释,但真正搞懂的只有那几行"为什么这么写";注释是索引,不是知识 |
| **换行符 LF / CRLF** | 仓库是 CRLF;`.bat` 用 LF 时 `goto`/标签有兼容风险,所以必须转回去 |
| **DPI 缩放** | 显示 150% + 程序不声明 DPI 感知 → 逻辑 1280×655 被 DWM 拉到物理约 1920×983(实测内存行/屏幕像素斜率 **0.667**),画面偏糊,还白付一份缩放开销 |
