## 三、今天写的代码,逐块含义

### 1. 文件顶部

```c
#include <windows.h>
LRESULT CALLBACK WindowProc(HWND, UINT, WPARAM, LPARAM);
```

- 只 `#include <windows.h>` 就够,不需要手动加任何 `.lib`(见第五节)
- `CALLBACK` = `__stdcall` 的别名。因为是"**系统调用你**",调用约定必须和系统一致 —— 漏掉它在 x86 下会报 `无法解析的外部符号 _WinMain@16`

### 2. `WindowProc`:五个分支

| 消息 | 什么时候来 | 现在干什么 |
|---|---|---|
| `WM_SIZE` | 窗口尺寸变化 | 只打印一行(占位)。等有后备缓冲后要在这里按新尺寸重建 |
| `WM_CLOSE` | 用户点 X / Alt+F4 | **只打印** —— ⚠️ 见"遗留问题":现在窗口关不掉 |
| `WM_DESTROY` | 窗口正在被销毁 | `PostQuitMessage(0)` —— **程序该退出的正确位置** |
| `WM_ACTIVATEAPP` | 本程序进入/离开前台 | 只打印一行(为后面"窗口失焦时怎么办"做准备) |
| `WM_PAINT` | 窗口有一块"脏了"需要重画 | 涂白/涂黑(今天新写的,见下) |
| `default` | 其他所有消息 | `Result = DefWindowProc(...)` —— **绝对不能省** |

**为什么 `default` 里必须调 `DefWindowProc`**:系统的默认行为(拖动窗口、最小化、重绘、Alt+Tab 切换……)全在这个函数里。不调用它,窗口会出现"拖不动 / 最小化后回不来 / 画面糊掉"这类怪毛病。

**两种写法都对**,但含义不同:

```c
// 风格 A(本工程,Casey 的写法):只把没处理的消息交给系统
LRESULT Result = 0;
switch (Message) { ... default: Result = DefWindowProc(...); break; }
return Result;

// 风格 B:switch 里只管自己关心的,最后统一交出去
switch (Message) { case WM_DESTROY: PostQuitMessage(0); break; }
return DefWindowProc(Window, Message, WParam, LParam);
```

风格 A 意味着:**凡是 switch 里列出来的消息,我完全接管,不让系统插手**。这正是今天那个 `WM_CLOSE` 坑的根源。

### 3. `WM_PAINT` 内部(今天新写的重点)

```c
case WM_PAINT:
{
    PAINTSTRUCT Paint;
    HDC DeviceContext = BeginPaint(Window, &Paint);   // ① 拿画布 + 拿到"脏区域"

    int X = Paint.rcPaint.left;                       // ② 从 rcPaint 拆出矩形
    int Y = Paint.rcPaint.top;
    int Width  = Paint.rcPaint.right  - Paint.rcPaint.left;
    int Height = Paint.rcPaint.bottom - Paint.rcPaint.top;

    static DWORD Operation = WHITENESS;               // ③ 记住上次用的颜色
    PatBlt(DeviceContext, X, Y, Width, Height, Operation);   // ④ 涂满这个矩形
    if (Operation == WHITENESS) { Operation = BLACKNESS; }
    else                        { Operation = WHITENESS; }

    EndPaint(Window, &Paint);                         // ⑤ 收尾(必须成对)
} break;
```

| 要点 | 说明 |
|---|---|
| `Paint.rcPaint` | **系统告诉你哪一块脏了**。只重画这一块才省性能 —— 这是正规做法,不是每次涂整屏 |
| `BeginPaint` 还干了第三件事 | 不只是给画布 + 填 `PAINTSTRUCT`,它**还把这块区域的"脏标记"清掉**(这正是 `DefWindowProc` 默认处理本该做的事) |
| `static` | 局部变量加 `static` 只初始化一次,之后每次进来都保留上次的值 → 于是每重画一次就换一种颜色 |
| `WHITENESS` / `BLACKNESS` | **光栅操作码**,不是颜色值(`0x00FF0062` / `0x00000042`)。意思是"不管当前画笔画刷,直接把目标涂成白/黑",所以**不需要先 `SelectObject` 选画刷** |
| 现象 | 拖动窗口大小 / 最小化再还原 / 被遮挡再露出时,窗口**在黑白之间交替闪** —— 这就是"肉眼确认 `WM_PAINT` 真的被调用了"的实验 |
| 铁律 | 自己处理 `WM_PAINT` 就必须成对调 `BeginPaint`/`EndPaint`。**忘了 `EndPaint`,系统会认为你没画完,一条接一条地发 `WM_PAINT`,窗口疯狂重画、CPU 飙高** |

### 4. `WinMain`:四步

```
① 填一张"窗口类登记表"(WNDCLASS)—— 告诉系统:这类窗口用哪个函数处理消息
② RegisterClass(&WindowClass)      —— 把表交给系统登记(返回 0 = 失败)
③ CreateWindowEx(...)              —— 照这张表造出真正的窗口(类名必须一字不差)
④ 消息循环                          —— GetMessage → TranslateMessage → DispatchMessage
                                        │
                                        ▼
                            WindowProc(Window, Message, WParam, LParam)
                                        │
                            收到 WM_DESTROY → PostQuitMessage(0)
                                        → 队列里多一条 WM_QUIT
                                        → GetMessage 返回 0 → 循环结束 → 进程退出
```

**关键理解**:程序的主体不是"我主动去读输入",而是"**系统把发生的事送进 `WindowProc`**"。这就是"消息驱动"。

### 5. 消息循环(你今天改成的那版)

```c
MSG Message;
for (;;)
{
    BOOL MessageResult = GetMessage(&Message, 0, 0, 0);
    if (MessageResult > 0) {          // >0 = 取到消息
        TranslateMessage(&Message);
        DispatchMessage(&Message);
    }
    else {                            // 0 = WM_QUIT(该退出); -1 = 出错
        break;
    }
}
```

| 函数 | 作用 |
|---|---|
| `GetMessage` | 从本线程消息队列取一条。**队列空时阻塞**(让出 CPU,不烧 CPU)。返回值:`>0` 有消息;`0` 收到 `WM_QUIT`;`-1` 出错 |
| `TranslateMessage` | 把 `WM_KEYDOWN`/`WM_KEYUP` 翻译成 `WM_CHAR`,这样能直接拿到"用户打了哪个字符"。以后做键盘输入靠它 |
| `DispatchMessage` | 把消息投递给该去的窗口过程。**系统就是在这一步回调你的** |

外层那两个 `if`(`RegisterClass` 返回值、`CreateWindowEx` 返回值)都有用:创建失败时返回 0,如果直接进消息循环,就变成"一个看不见的窗口,程序却永远不退出"。

## 四、今天搞懂的概念

| # | 概念 | 一句话 |
|---|---|---|
| 1 | `WNDCLASS` = 窗口的**登记表** | 想开窗口必须先填表备案;`= {0}` 不能省,局部变量不清零就是栈上垃圾值 |
| 2 | `lpfnWndProc = WindowProc` | 右边**不加括号** = 交的是**函数地址**;"谁处理这件事"推迟到运行时决定 |
| 3 | **callback(回调)** | 因为"打电话的人不是你,是系统"。`add-hook`(Emacs)、`qsort` 的比较函数、`CreateThread` 都是同一个套路 |
| 4 | 函数指针 | `typedef LRESULT (CALLBACK* WNDPROC)(HWND, UINT, WPARAM, LPARAM);` —— 参数/返回值/调用约定全写死,对不上就编译不过 |
| 5 | 字符集 → A/W 版本 | MultiByte 下 `WNDCLASS` = `WNDCLASSA`,`lpszClassName` 是 `LPCSTR` → 写 `"..."`;Unicode 下是 `LPCWSTR` → 必须写 `L"..."` |
| 6 | 子系统 → 入口 | Windows 子系统找 `WinMain`,Console 子系统找 `main`。填错就是 `LNK2019` |
| 7 | **DC(设备上下文)** | 一块"画布"外加当前所有绘图设置。`CS_OWNDC` = 每个窗口一块私有画布,设置能留住;`CS_CLASSDC` = 全类共用一块,**微软明确说别用**(16 位 Windows 遗留) |
| 8 | **`.lib` 与 `.dll`** | `.lib` 是**链接时**的"介绍信",`.dll` 是**运行时**真正装代码的地方。系统 DLL 永远不用分发 |
| 9 | 文档的 Syntax 块 ≠ 调用代码 | 那是"函数原型"(全是类型和占位名)。抄进代码就是今天那个 `C2275: "UINT": 应为表达式而不是类型` |
| 10 | 回调里别长时间阻塞 | 你在 `WindowProc` 里耗时,系统就得等你返回才能派发下一条 → 窗口"未响应"。(以后改 `PeekMessage` 就是为了把活儿搬出回调) |

## 五、今天踩的坑(速查)

| 现象 / 错误 | 真正原因 | 解法 |
|---|---|---|
| `C3193: "__clrcall": 需要"/clr"或"/ZW"` | 微软文档里 `WinMain` 的签名块写错了(2019 年文档迁移事故,**至今未修**) | 用 `WINAPI` / `APIENTRY` / `CALLBACK` |
| `C3115` / `C4467`: `"in"` 特性不允许使用 | 把文档里的 `[in]`、`[in, optional]` 方括号写法抄进本机 C++ | 本机 C++ 用 SAL 宏 `_In_` / `_In_opt_`,或不写 |
| `C2664: 无法将参数从 "const char [N]" 转换为 "LPCWSTR"` | 字符集是 Unicode,窄字符串喂给了 `...W` 版函数 | 改 MultiByte(已改),或用 `L"..."` |
| `C2373: "WinMain": 重定义;不同的类型修饰符` | 自己声明的 `WinMain` 和 `winbase.h` 里的冲突 | 加 `WINAPI`,别重复声明 |
| `C2275: "UINT": 应为表达式而不是类型` | **把"函数声明"当成"函数调用"抄了**(`BOOL WINAPI GetMessage(&Message, 0, UINT a, UINT b);`) | 调用只写**值**:`GetMessage(&Message, 0, 0, 0)` —— 声明要类型,调用要值 |
| `LNK2019: 无法解析的外部符号 main` | 子系统是 Console,但只提供了 `WinMain` | 链接器 → 系统 → 子系统改成 Windows |
| `LNK2019: 无法解析的外部符号 _WinMain@16` | x86 下 `WinMain` 没加 `__stdcall` | 加 `WINAPI`(x64 下调用约定被忽略,不会出这个错) |
| `LNK2019: 无法解析的外部符号 XXX`(某个 API) | 少了提供它的 `.lib` | 链接器 → 输入 → 附加依赖项,或代码里 `#pragma comment(lib, "xxx.lib")` |
| 窗口不出现,`CreateWindowEx` 返回 0 | 类名和注册时写的不是同一个字符串 | 用同一个变量存类名 |
| 窗口一闪而过 / 程序立刻退出 | 少了消息循环,或没给 `WS_VISIBLE` | 补上 |
| 窗口拖不动、最小化后回不来、画面糊 | `default` 分支没调 `DefWindowProc` | 补上 |
| **点 X 关不掉窗口**(今天实测确认) | `case WM_CLOSE` 只打印就 `break`,**没有落到 `default`**,所以 `DefWindowProc` 不会执行,而"销毁窗口"正是默认处理的活 | 见下面"遗留问题" |
| 运行了什么都没发生 | Windows 子系统没有控制台,`printf` 看不到 | 用 `OutputDebugStringA` + DebugView |

## 六、遗留问题 & 下次要做

### ⚠️ 1. 现在点 X 关不掉窗口(今天实测确认)

实测:给窗口发 `WM_CLOSE`(点 X 就是这个动作)之后,进程仍然活着。原因:

```c
case WM_CLOSE:
{
    OutputDebugStringA("WM_CLOSE\n");
} break;      // ← 这里 break 了,DefWindowProc 不会被调用
```

微软文档原文:"By default, the **DefWindowProc** function calls the **DestroyWindow** function to destroy the window."
**销毁窗口是"默认处理"干的活** —— 把它拦下来又不自己销毁,`WM_DESTROY` 就永远不来,`PostQuitMessage(0)` 永远不执行。

两种改法(挑一个):

```c
case WM_CLOSE: { PostQuitMessage(0); } break;      // Casey 的做法:直接退出程序
// 或者
case WM_CLOSE: { DestroyWindow(Window); } break;   // 文档示例的做法:销毁窗口 → WM_DESTROY 里 PostQuitMessage
```

| 项目 | 值 |
|---|---|
| 工程真实位置 | `C:\THOTH\DaiMaXuNiJi\NEWCODE\HandMade\` |
| **`D:` 盘** | 是 `subst` 映射:`D:\` → `C:\THOTH\DaiMaXuNiJi\NEWCODE`(所以 `D:\HandMade\...` 和 `C:\THOTH\...\HandMade\...` 是**同一批文件**) |
| 为什么要这个映射 | Casey 的配置/脚本里路径都写死成 `D:/HandMade/HandMade/...` |
| 说明文档 | `D:\HandMade\explain\<年-月>\<年-月-日>.md` |
| `shell.bat` | 开一个带 VS2022 环境的命令行(项目目录也加进 PATH) |
| `emacs.bat` | 在带 VS 环境的情况下启动 Emacs。⚠️ **不要学 Casey 加 `-q -l`** —— 那会跳过 `init.el`,你的键位全丢 |
| `build.bat` | Emacs 里 `M-m` 编译 → `build\win32_handmade.exe`;自带 `VsDevCmd`;`-W4 -WX`;`-MTd` 静态 CRT |
| 关键工程设置 | 字符集 **MultiByte**、子系统 **Windows**、工具集 v143、警告等级 `/W3` |
| lib | **一个都不用手动加**。VS 默认已链:`kernel32;user32;gdi32;winspool;comdlg32;advapi32;shell32;ole32;oleaut32;uuid;odbc32;odbccp32`。以后音频要 `winmm.lib`、手柄要 `xinput.lib`、D3D 要 `d3d11.lib`+`dxgi.lib` |
| 实用命令 | `dumpbin /dependents x.exe`(看运行时依赖)、`dumpbin /headers x.exe`(看子系统/入口点)、`where cl` + `cl`(看编译器版本) |
