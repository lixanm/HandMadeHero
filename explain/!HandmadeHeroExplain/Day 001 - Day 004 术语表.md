## 0. 先立三个最底层的概念

| 术语 | 解释 |
|---|---|
| **bit(位)** | 电脑里最小的单位,只能是 0 或 1 |
| **byte(字节)** | 8 个位 = 1 个字节,能表示 **0~255** 这 256 个数。颜色、字符长度都用它衡量 |
| **内存(memory)** | 一长串编号的字节。所谓"地址"就是这个串里的编号 |

> 记住"1 字节 = 0~255"这一条,后面 RGB、32bpp 全都通了。

## 1. 像素与颜色

| 术语 | 解释 |
|---|---|
| **pixel(像素)** | 屏幕上最小的一个方点。一个画面就是几百万个这样的点 |
| **resolution(分辨率)** | "多少列 × 多少行个点",比如 1920×1080 |
| **RGB** | 一个颜色的表示法:红、绿、蓝各有多亮(**各 0~255**)。`RGB(255,0,0)`=纯红,`RGB(0,0,0)`=黑,`RGB(255,255,255)`=白 |
| **alpha(A)** | 透明度。图形编程里常写成 RGBA,但**我们现在没用**,第 4 个字节是空的 |
| **24 位色 / 32bpp** | 24 位 = 一个像素 3 字节(RGB 各 8 位)。**32bpp** = 一个像素 4 字节,多出的那个字节不用,目的是**对齐**(2 的整数次幂,存取更快) |
| **BGRA 顺序** | 32bpp 内存里一个像素 4 个字节的**实际排列顺序是 蓝、绿、红、空**。📍`*Pixel++ = 0x00996633;` 这个值的读法是"蓝 0x33、绿 0x66、红 0x99" → 屏幕上显示成棕橙色 |
| **颜色值 0x00996633** | 就是一个整数:`0x00` `99` `66` `33`。因为 x86 是**小端**(低位字节存低地址),内存里写成 `33 66 99 00` = 蓝绿红空 |
| **frame buffer(帧缓冲)** | **显卡里存着整个屏幕画面的那块大内存**。它每秒钟被读出来显示 60~144 次 → 所以你看到的画面是动的。"把画面显示到屏幕上"本质就是"把我们的位图复制进帧缓冲" |

## 2. 位图(bitmap)—— 本项目的核心

| 术语 | 解释 |
|---|---|
| **bitmap(位图)** | 字面是 **bit + map = "每个点是什么颜色的记录表"**。在内存里它**就是一块普通的连续字节**,排法是"一行接一行、每行从左到右" |
| **位图 vs 矢量图** | 矢量图存的是"从(0,0)画线到(100,50)"这种**命令**;位图存的是"每个点啥颜色"。**屏幕只认位图**,所以游戏渲染的最终产物一定是位图 |
| **stride(跨距)** | 位图**一行**占多少字节。我们这里是 `宽度 × 4`。📍`Row += BitmapWidth * 4;` —— 就是"挪到下一行" |
| **数据指针** | 位图内存的起始地址。📍`BitmapMemory` |
| **bottom-up(自下而上)/ top-down(自上而下)** | 由 `biHeight` 的**正负**决定:正数 = 自下而上(内存第一行是画面**最下面**那行);负数 = 自上而下(第一行就是最上面那行)。📍Day 3 我们填的正数,**Day 4 改成了负数**(见 §11) |
| **pitch** | 和 stride 基本同义(有些地方特指"字节跨距") |
| **DIB(设备无关位图)** | Device Independent Bitmap。强调"设备无关"是因为**同一张位图可以给屏幕也可以给打印机**。📍Day 3 用 `CreateDIBSection` 拿它;**Day 4 起改成自己 `VirtualAlloc`,只留 `BITMAPINFO` 描述格式**(见 §11) |
| **DDB(设备相关位图)** | 老式位图,只能在特定设备上用。现在基本不用了 |
| **section(节/段)** | `CreateDIBSection` 里的词,意思是"从内存里分出来的一段"。这个函数名的意思就是"给我分一段能当位图用的内存" |
| **BITMAPINFO** | 一张"位图说明书"结构体:`bmiHeader`(头部信息)+ `bmiColors`(调色板,我们不用) |
| **BITMAPINFOHEADER** | 说明书里的**头部**:宽、高、每像素几位、压不压缩…… 📍`BitmapInfo.bmiHeader.biWidth = ...` |
| **biWidth / biHeight** | 位图的宽和高(以像素为单位) |
| **biBitCount** | 每个像素多少位。我们填 **32** |
| **biPlanes** | 位平面数,**老概念,现在必须填 1** |
| **biCompression / BI_RGB** | 压不压缩。`BI_RGB` = **不压缩**(我们要写得快、贴得快,任何压缩都是负担) |
| **palette(调色板)/ palettized(调色板化的)** | 缓冲区里存"颜色编号",再去一张表里查真正的颜色。**当年为了省内存**,现在不用了。我们没有调色板,所以那些字段全是 0 |
| **RGBQUAD** | `BITMAPINFO` 里放调色板项的类型(红绿蓝各一字节 + 空一字节)。我们用不到 |

## 3. 缓冲区与双缓冲

| 术语 | 解释 |
|---|---|
| **buffer(缓冲区)** | **通用词**:"先存起来、稍后再用的一块内存"。跟位图没关系 —— 以后还会听到"键盘缓冲区""文件缓冲区" |
| **backbuffer(后备缓冲)** | "后面那张图":**我们自己先在内存里画好的那张位图**。📍`BitmapMemory` |
| **front buffer(前台缓冲)** | 用户正在看的那张(屏幕/帧缓冲) |
| **double buffering(双缓冲)** | 后备图 + 前台图的组合。**为什么要它**:直接往屏幕上画,用户会看到你"画到一半"的画面(闪烁、撕裂)。先在后备图上慢慢画好,再**一次性** blit 上去,用户永远只看到完整画面。就像画家先在后台画完再举给观众看 |
| **invalid region(脏区域)** | 系统认为"这块内容不对了、需要重画"的区域。窗口被遮挡后再露出来、被拖动、尺寸变化,都会产生脏区域。📍`Paint.rcPaint` 就是它 |
| **InvalidateRect** | ⏳ 主动告诉系统"这块脏了,请给我发 WM_PAINT"。以后要"强制重画"时会用到 |

## 4. 设备上下文(DC)与 GDI

| 术语 | 解释 |
|---|---|
| **DC(设备上下文)** | Device Context。一个**"作画工具包"**:里面装着当前用哪支笔、什么颜色、什么字体、只能在哪块区域画(裁剪区)等等。调用画图函数时它替你保管这些状态 |
| **HDC** | DC 的**句柄**(h = handle) |
| **memory DC(内存 DC)** | 一块**内存里的画布**(而不是屏幕)。⚠️ 因为我们用 `StretchDIBits`(**直接收像素指针**),所以**根本不需要它**;Day 4 已把它删掉 |
| **CreateCompatibleDC(0)** | 造一个"和屏幕兼容"的 DC。**只有用 `BitBlt`(DC→DC)才需要** —— `StretchDIBits` 不需要,见 §5 |
| **GDI** | Graphics Device Interface,Windows 那套绘图 API 的总称(`PatBlt`、`StretchDIBits`、`TextOut`、`LineTo`……)。我们说"尽量少用 GDI"= **不要用 GDI 画图形**,只让它最后做一次 blit |
| **GDI object(GDI 对象)** | 通过 GDI 创建的资源:位图、画刷、笔、字体……它们都占系统资源,**用完要删** |
| **brush(画刷)** | 填充用的一支"大刷子"(`hbrBackground` 就是"擦背景用的画刷") |
| **DeleteObject** | GDI **统一的删除入口**:位图、画刷、笔都传给它,它自己判断类型。📍`DeleteObject(BitmapHandle);` —— 位图句柄本身就管着那块内存,删它顺带释放内存 |
| **BeginPaint / EndPaint** | WM_PAINT 里的**成对调用**:`BeginPaint` 给你画布(DC)+ 填 `PAINTSTRUCT` + **把脏标记清掉**;`EndPaint` 收尾。⚠️ 忘了 `EndPaint` → 系统以为你没画完,一直发 WM_PAINT,CPU 飙高 |
| **PAINTSTRUCT** | `BeginPaint` 填给你的一张表,里面有 `hdc`(画布)和 `rcPaint`(脏区域) |

## 5. 从位图到屏幕:blit 与 StretchDIBits

| 术语 | 解释 |
|---|---|
| **blit** | 读作"布利特",**bit block transfer(位块传送)** 的缩写:把一整块矩形像素从 A 复制到 B。为什么专门有个词?因为"整块搬"比"逐个像素画到屏幕上"快得多 |
| **BitBlt** | 1:1 搬(不缩放)。⚠️ 它只收 **DC→DC**,所以用它就必须先建 DC、让 Windows 分配位图 —— **Day 4 就是因此换掉了它** |
| **StretchDIBits** | 搬的时候**还能拉伸/缩放**(stretch),而且**直接收像素指针**(不需要 DC、不需要位图句柄)。📍`win32UpdateWindow()` 里那一次调用,Day 4 起改成**每帧**调一次 |
| **rop / raster operation(光栅操作码)** | 决定"怎么合并"的代码:XOR、AND、直接覆盖…… 我们要的就是**直接覆盖** |
| **SRCCOPY** | 最常用的那个 rop = "把源直接拷过去,不做任何位运算"。📍`StretchDIBits(..., SRCCOPY);` |
| **DIB_RGB_COLORS** | "我这个缓冲是直接 RGB,不是调色板"的标志。**创建和 blit 时必须填一致** |
| **WHITENESS / BLACKNESS** | 也是光栅操作码 ="不管当前画刷,直接把目标涂成白/黑"。📍以前 `PatBlt` 用它俩做黑白闪烁,现在被 `StretchDIBits` 取代了 |
| **PatBlt** | "Pattern Block Transfer",拿当前画刷往一块矩形里刷图案/颜色。📍**我们已经删掉它了** |

## 6. 窗口与消息(Win32 平台层)

### 6.1 开局四步

| 术语 | 解释 |
|---|---|
| **entry point(入口点)** | 程序开始执行的地方。**Windows 子系统**下入口是 `WinMain`,**控制台子系统**下是 `main`。📌填错子系统就是 `LNK2019: 无法解析的外部符号 main` |
| **WinMain** | Win32 图形程序的入口函数。📌微软文档里那段 `__clrcall` 的签名是**文档的错** |
| **subsystem(子系统)** | 链接器选项,告诉 Windows"这是控制台程序还是图形程序" |
| **WNDCLASS(窗口类)** | 一张**"窗口登记表"**:告诉系统"这类窗口用哪个函数处理消息、配什么图标光标"。📍`WNDCLASS WindowClass = {0};` |
| **RegisterClass** | 把这张表**交给系统备案**(返回 0 = 失败) |
| **window class(窗口类)** | 备案后的那份"模板"。同一类的窗口可以有多个,它们**共用一个消息处理函数** |
| **CreateWindowEx** | 照备案的模板**造出一个真正的窗口**(12 个参数)。返回 0 = 失败 |
| **CW_USEDEFAULT** | 位置/尺寸参数填它 = "系统你替我决定" |
| **WS_OVERLAPPEDWINDOW** | 窗口样式:标题栏 + 边框 + 最大化 + 最小化 + 关闭,一整套标准组合 |
| **WS_VISIBLE** | 窗口样式:创建完**直接显示**(不然要自己调 ShowWindow) |
| **class style(类样式)** | 窗口类的整体行为标志:`CS_HREDRAW`/`CS_VREDRAW`(宽高变化时整窗重画)、`CS_OWNDC`(给窗口一块私有画布)、`CS_CLASSDC`(全类共用一块画布 —— **微软明确说别用**) |

### 6.2 消息机制

| 术语 | 解释 |
|---|---|
| **message(消息)** | Windows 把"发生了一件事"(按键、鼠标、被关掉……)打包成一条消息 |
| **WM_ 前缀** | Window Message。所有窗口消息都是 `WM_xxx` |
| **消息队列(message queue)** | 每个线程一条队列,系统往里塞消息,你往外取 |
| **消息循环(message loop)** | 你不停从队列取消息、翻译、派发的那段循环。📍`while (Running) { GetMessage... }` |
| **GetMessage** | 从队列取**一条**。返回值:`>0` 有消息 / **`0` 收到 WM_QUIT(该退出)** / `-1` 出错。**队列空时会阻塞**(让出 CPU,不烧 CPU) |
| **PeekMessage** | 和 GetMessage 类似,但**不阻塞**:没有消息也立刻返回。📍Day 4 起游戏主循环用的就是它 |
| **PM_REMOVE** | `PeekMessage` 的最后一个参数 ="把消息**取走**"。📍每帧用一个内层 `while` 把队列排空 |
| **游戏循环(game loop)** | 每帧都要跑一遍的循环:排空消息 → 渲染 → blit → 下一帧。📍Day 4 写出来的 |
| **GetDC / ReleaseDC** | 向窗口**借/还**一块画布(DC),**必须成对**。📍Day 4 在主循环里每帧 blit 用它 |
| **TranslateMessage** | 把 `WM_KEYDOWN`/`WM_KEYUP` 翻译成 **`WM_CHAR`**(这样能直接拿到"用户打了哪个字符") |
| **DispatchMessage** | 把消息**投给对应的窗口过程** —— **系统就是在这一步回调你的函数的** |
| **PostQuitMessage** | 往队列里塞一条 `WM_QUIT`(让消息循环退出)。📍以前 WM_DESTROY 里用它,现在改成 `Running = false` |
| **WindowProc(窗口过程)** | 你写的**回调函数**,系统把发给本窗口的每条消息都送进这里 |
| **DefWindowProc** | 系统的**默认处理**。拖动窗口、最小化、重画这些默认行为全在它里面。📍`default:` 分支。⚠️ 不调用它 → 窗口拖不动、重画乱套 |
| **回调(callback)** | "把函数地址交给别人,让别人在它认为合适的时候回头调用你"。`lpfnWndProc` 就是最经典的例子 |
| **lpfnWndProc** | WNDCLASS 里存"消息处理函数地址"的那一格(类型是 `WNDPROC`,也就是函数指针)。⚠️ 写 `= WindowProc;` **不加括号** = 交地址;加括号 = 立刻调用(错) |

### 6.3 你处理过的消息

| 消息 | 什么时候来 | 你干什么 |
|---|---|---|
| **WM_SIZE** | 窗口尺寸变了 | `GetClientRect` 拿新尺寸 → `ResizeDIBSection` |
| **WM_CLOSE** | 用户点了 X / Alt+F4 | `Running = false`。⚠️ 空的 case 会把"销毁窗口"这件默认处理的活拦下来 |
| **WM_DESTROY** | 窗口正在被销毁 | `Running = false` |
| **WM_ACTIVATEAPP** | 本程序进入/离开前台 | 只打印(以后要在这里暂停游戏) |
| **WM_PAINT** | 窗口有一块脏了 | `BeginPaint` → `win32UpdateWindow` → `EndPaint` |
| **WM_QUIT** | 系统告诉你"该退出了" | 用 `GetMessage` 时不用管它(返回 0 就是它);**换成 `PeekMessage` 后必须自己检查它**并把 `Running = false` |

### 6.4 窗口尺寸相关

| 术语 | 解释 |
|---|---|
| **client area(客户区)** | 窗口里**你能画的那个矩形**(不含标题栏、边框)。📍`GetClientRect(Window, &ClientRect);` |
| **window rect(窗口矩形)** | **整个窗口**(含标题栏边框)。对应的函数是 `GetWindowRect` —— 我们不要它,因为边框归 Windows 管 |
| **RECT** | 一个矩形结构体:`left` / `top` / `right` / `bottom`(存的是**边缘坐标**,不是宽高) |
| **脏区域 rcPaint** | 见 §3。`Paint.rcPaint` 用它算出 X/Y/宽/高 |

## 7. 句柄(HANDLE)与匈牙利命名

| 术语 | 解释 |
|---|---|
| **handle(句柄)** | 系统发给你的一个**编号牌**。你拿着牌子去办事,不用关心背后是什么。窗口、位图、DC、文件……都是句柄 |
| **HINSTANCE** | 程序实例的句柄(Win32 里基本等于"这个 exe 在内存里的基址") |
| **HWND** | 窗口句柄 |
| **HDC** | 设备上下文句柄 |
| **HBITMAP** | 位图句柄 |
| **HICON / HCURSOR / HBRUSH** | 图标 / 光标 / 画刷的句柄 |
| **hPrevInstance** | Win16 时代遗留的参数,**Win32 里永远是 NULL** |
| **匈牙利命名** | 名字前缀告诉你类型,老 Windows 代码里到处都是。常见前缀见下表 |

| 前缀 | 意思 | 你代码里的例子 |
|---|---|---|
| `h` | handle 句柄 | `hInstance`、`hWnd`、`hbmp` |
| `lp` / `p` | long pointer / pointer(16 位时代"长指针"的叫法,现在就是普通指针) | `lpCmdLine`、`lpszClassName` |
| `lpsz` | **l**ong **p**ointer to **z**ero-terminated **s**tring = "以 0 结尾的字符串指针" | `lpszMenuName`、`lpszClassName` |
| `cb` | **c**ount of **b**ytes 字节数 | `cbClsExtra`、`cbWndExtra` |
| `dw` | DWORD(32 位无符号整数) | `dwExStyle`、`dwStyle` |
| `b` / `f` | BOOL / flag 布尔 | `biPlanes` |
| `i` / `n` | int | `nShowCmd`、`nWidth` |
| `sz` | 以 0 结尾的字符串 | —— |

## 8. Windows 的那些类型名(全是别名)

| 类型 | 真身 | 一句话 |
|---|---|---|
| **BOOL** | `int`(4 字节) | ⚠️ **不是 C++ 的 bool**。0 = 假,非 0 = 真 |
| **UINT** | `unsigned int` | 32 位无符号 |
| **DWORD** | `unsigned long` | 32 位无符号("double word",一个 word = 16 位) |
| **LONG** | `long` | Windows 上**恒为 32 位**(哪怕是 64 位系统) |
| **LRESULT** | `LONG_PTR` | 窗口过程的返回值。**宽度跟着指针走**(x86 4 字节,x64 8 字节) |
| **WPARAM** | `UINT_PTR` | 无符号指针宽整数。含义**随消息变** |
| **LPARAM** | `LONG_PTR` | 有符号指针宽整数。含义**随消息变** |
| **LPCSTR** | `const char *` | ANSI 字符串(只读) |
| **LPSTR** | `char *` | ANSI 字符串 |
| **LPCWSTR** | `const wchar_t *` | Unicode 字符串(只读) |
| **__stdcall** | 一种调用约定 | 参数从右往左压栈、被调用者清理栈。`WINAPI` / `APIENTRY` / `CALLBACK` **都是它的别名** |

> **A 与 W**:Windows 里几乎所有收字符串的函数都有两个版本 —— `xxxA`(ANSI,单字节)和 `xxxW`(Wide,UTF-16)。你写泛型名 `xxx` 时,由**字符集设置**决定它变成哪个:**MultiByte → A**,**Unicode → W**。
> [!note]
> 我们工程是 **MultiByte**,所以字符串直接写 `"..."`;如果改成 Unicode,就得写 `L"..."`,否则报 `C2664 ... LPCWSTR`。

## 9. C 语言相关(代码里出现的)

| 术语 | 解释 |
|---|---|
| **`#include <windows.h>`** | 把 Windows 的声明全拉进来。**几乎所有的类型、常量、函数原型都在这里面** |
| **头文件(header)** | 存"声明"的文件。📌**签名以头文件为准**:在 VS 里对任何 API 按 **F12** 跳到真实声明(微软文档出过错,比如 `WinMain` 的 `__clrcall`) |
| **声明 vs 调用** | **声明**写给编译器看(`返回类型 名字(类型 参数名);`);**调用**写给程序跑(`名字(值, 值);`)。📌把文档的 Syntax 块(声明)抄进代码就会报 `C2275: "UINT": 应为表达式而不是类型` |
| **`#define`(宏)** | 编译前做的**纯文本替换**。`#define 新名字 被替换成的东西`,顺序**不能反** |
| **typedef** | 给类型起别名。`WNDPROC`、`LRESULT`、`HWND` 这些都是 typedef 出来的 |
| **函数指针** | 指向函数的指针。`lpfnWndProc` 就是 |
| **局部变量** | 函数内声明的变量,**躺在栈上**。⚠️ **不初始化就是垃圾值**(可能是上次调用留下的任何东西) |
| **`= {0}`** | 把整个结构体清零。📌`WNDCLASS WindowClass = {0};` 这一句**不能省**:`lpfnWndProc` 如果是垃圾值,系统一调用就崩 |
| **全局变量** | 函数外声明的变量。**`static` 全局会自动清零** |
| **`static` 的三种含义** | ① 函数内的 `static` 局部变量 = **值在离开作用域后保留**;② 文件级 `static` 全局 = 只在本文件可见;③ 函数前的 `static` = 这个函数只在本文件可见。⚠️ 同一个词三个意思,所以 Casey 定义了三个宏 |
| **`local_persist`** | 📍你自己加的宏 = `static`(**局部**持久变量) |
| **`global_variable`** | 📍你自己加的宏 = `static`(全局变量) |
| **`internal`** | 📍你自己加的宏 = `static`(文件内部函数) |
| **`void *`** | "我不在乎它指向什么类型的指针"。📍`BitmapMemory`。用的时候要**强制转换**成具体类型:转成 `unsigned char *` 做指针算术、转成 `unsigned int *` 一次写一个像素 |
| **强制类型转换(cast)** | `(uint32 *)Row` —— 告诉编译器"就把这块内存当这种类型看"。⚠️ `-W4 -WX` 下**必须显式转换**(否则"丢失数据"警告 = 编译失败) |
| **`uint8` / `uint16` / `uint32`** | 明确位宽的无符号整数(`unsigned char`/`short`/`int` 又长又不表达意思)。📍Day 4 起用它们写像素 |
| **`stdint.h`** | C 标准头文件,里面就有 `uint8_t` / `uint32_t`。老代码自己 typedef,现代代码可以直接用标准类型 |
| **指针算术(pointer arithmetic)** | 对指针 `+1` 时,C 会**偷偷乘上"所指类型的大小"**。所以行指针常用 `uint8 *`(每次 +1 就是 +1 字节) |
| **翻译单元(translation unit)** | 一个 `.cpp` **加上它 include 的所有头文件**,编译时算一个整体。`static` 的"文件内部可见"严格说是"翻译单元内部可见" |
| **`extern`** | 声明"这个全局变量在别的翻译单元里"。别的文件写 `extern int foo;` 就能访问它 —— 和 `static` 正好相反 |
| **小端(little-endian)** | x86 上低位字节存在低地址。所以 `0x00996633` 在内存里是 `33 66 99 00` |

| 术语 | 解释 |
|---|---|
| **编译(compile)** | 把 `.cpp` 变成 `.obj`(机器码) |
| **链接(link)** | 把 `.obj` + 各种库拼成 `.exe` |

| **user32 / gdi32 / kernel32** | 分别管:窗口与消息 / 绘图 / 进程线程文件等底层。📍我们调的函数主要来自这三个 |

| **`-WX`(警告当错误)** | 任何警告都当成编译失败。📍你的 `build.bat` 就是这么设的 —— 新代码有警告就编不过 |
| **`-FC`** | 报错信息里带**完整文件路径**(而不是只有文件名)。📍我们的工程里已经开了 —— VS 里双击错误 / 错误列表就能跳到出错那一行 |
| **`-MTd` / `/MDd`** | 运行库链接方式:**静态**(把 CRT 编进 exe,拷到哪都能跑)/ **动态**(依赖 `VCRUNTIME140.dll`) |
| **CRT** | C Runtime,C 运行库。`printf`、启动代码这些都在里面 |
| **`dumpbin /dependents x.exe`** | 看这个 exe **运行时依赖哪些 DLL** |
| **`dumpbin /exports x.dll`** | 看某个 DLL **导出了哪些函数** |
| **subsystem(子系统)** | 见 §6.1。Console 找 `main`,Windows 找 `WinMain` |

### 见过的错误码 → 它其实在说什么

| 报错 | 真正的原因 |
|---|---|
| `C3193: "__clrcall": 需要"/clr"或"/ZW"` | 抄了微软文档里 C++/CLI 风格的签名 |
| `C3115 / C4467: "in" 特性不允许使用` | 抄了文档里的 `[in]` 方括号 SAL 写法(本机 C++ 要用 `_In_`) |

## 11. 内存与游戏循环(Day 4 新增)

### 11.1 自己分配内存

| 术语 | 解释 |
|---|---|
| **VirtualAlloc** | 向系统**直接**要内存(按页)。📍`BitmapMemory = VirtualAlloc(0, Size, MEM_COMMIT, PAGE_READWRITE);` |
| **page(页)** | 内存分配的**最小单位**,Windows 上一页通常 **4096 字节**。只要 100 字节也会给你一整页 |
| **虚拟地址空间(virtual address space)** | 每个进程看到的一片"连续的"地址(64 位下非常大),由系统在背后映射到物理内存 |
| **物理内存 / 页表(page table)** | 真正的内存条 / 系统记录"哪个虚拟页对应哪块物理内存"的那张表 |
| **reserve(保留)** | 只把地址范围占住,系统**还不真的给你内存**(`MEM_RESERVE`) |
| **commit(提交)** | 真的开始跟踪这块内存、把它接到物理内存上(`MEM_COMMIT`)。📍我们用的就是它 |
| **decommit(取消提交)** | 停止跟踪,但**保留地址范围**(`MEM_DECOMMIT`) |
| **VirtualFree / MEM_RELEASE** | 整块还给系统。📍释放旧 backbuffer 时用;大小可以传 0(系统记得) |
| **PAGE_READWRITE** | 内存保护属性:可读可写。**不需要执行权限**(我们不在里面跑代码) |
| **VirtualProtect / PAGE_NOACCESS** | 改内存保护属性。**调试技巧**:释放时先设成"完全不可访问",这样还有旧指针来写就会**当场炸在你自己的那一行**(否则是个极难查的 use-after-free) |
| **PAGE_WRITECOPY(写时复制)** | 先和别的进程共享同一份物理内存,**一旦有人写就偷偷复制一份新的给他**。主要是为了实现 Unix 的 `fork()` 才进 Windows 的 |
| **HeapAlloc / malloc / new** | 层级不同:`malloc`/`new`(CRT 分配器)→ `HeapAlloc`(系统堆)→ **最终也是 `VirtualAlloc`(按页)**。所以直接调 `VirtualAlloc` 是"少绕两层" |
| **栈(stack)vs 页分配** | 栈上的变量**函数一返回就没了**,所以"要活过这个函数"的数据**不能放栈上** —— 这就是需要分配的原因 |

### 11.2 内存布局相关(补充)

| 术语 | 解释 |
|---|---|
| **pitch(行距)** | 从"这一行开头"到"下一行开头"要加的**字节数**。📍`Row += Pitch;` |
| **stride(跨距)** | 从"这一行结尾"到"下一行结尾"要加的字节数。日常常和 pitch 混着用 |
| **每行填充(padding)** | 有些格式**每行末尾有填充字节**(为了对齐),这时 pitch ≠ 宽 × 每像素字节数 |
| **未对齐访问(unaligned access)** | 4 字节的值没落在 4 的倍数地址上,x86 上**有性能惩罚**。这就是宁可要 32bpp(每像素 4 字节,天然对齐)也不要 24bpp 的原因 |
| **BGR 内存顺序** | Windows 位图内存里的顺序是 **蓝、绿、红、pad**。原因:小端机器上"内存按 R,G,B 排"读进寄存器会变成 B,G,R,而 Windows 的作者希望**在寄存器里看是 R,G,B**,于是干脆把内存顺序反着定义。pad 留在最高位,是因为他们只在乎 R/G/B 的相对顺序 |
| **溢出回绕(wrapping)** | `uint8` 的 255 再加 1 就回到 0。📍渐变里"每 256 像素颜色跳回 0"就是它。他说:**有意为之的溢出是完全正当的用法** |
| **layered window(分层窗口)** | 让窗口支持 alpha(透明)的模式 —— **那时那个 pad 字节就可以当 alpha 通道用** |

### 11.3 渲染循环

| 术语 | 解释 |
|---|---|
| **帧(frame)** | 一次完整的"渲染 + 显示"。60 帧/秒 = 每秒画 60 张 |
| **每帧渲染** | 主循环里**无条件**地渲染 + blit(不再等 WM_PAINT) |
| **内层排空队列** | 一帧里先用 `while (PeekMessage(..., PM_REMOVE))` 把所有积压消息处理完,再渲染。不排空队列程序行为会变怪 |
| **阻塞 vs 非阻塞** | `GetMessage` 阻塞(没消息就睡)、`PeekMessage` 非阻塞(没消息也立刻返回)。**游戏要一直跑,所以用后者** |

## 附录 A:我们代码的一条数据流(把术语串起来)

```
VirtualAlloc                        ← Day 4 起改成自己分配(Day 3 用的是 CreateDIBSection)
    │  "给我一块内存当位图用"(按页对齐)
    ▼
BitmapMemory ─── 一块 1280×655×4 字节 ≈ 3.2 MB 的内存(bitmap / backbuffer)
    │
    │  我们按"每 4 字节一个像素(BGRA)、一行一行"的约定往里写颜色
    │  *Pixel++ = ((Green << 8) | Blue);   ← 这一步就叫"渲染"(Day 4 的渐变就是这样写的)
    ▼
一块填满颜色的位图
    │
    │  StretchDIBits(窗口DC, ..., BitmapMemory, ..., SRCCOPY)   ← blit(Day 4 起每帧一次)
    ▼
屏幕那块区域的 frame buffer
    │
    │  显卡每秒钟把它读出来 60 次
    ▼
你看到的:一个棕橙色的窗口
```

**另一条线(谁在什么时候叫我们):**

```
Windows 发现窗口脏了
    → 往消息队列塞一条 WM_PAINT
        → 我们的消息循环 GetMessage 取到它
            → TranslateMessage(对键盘消息做翻译)
                → DispatchMessage 查到这个窗口的 lpfnWndProc 地址
                    → 调用 WindowProc(Window, WM_PAINT, 0, 0)
                        → BeginPaint 拿到 DC 和脏区域(rcPaint)
                            → win32UpdateWindow(...)   ← blit
                        → EndPaint
```

**Day 4 起,主循环不再等 WM_PAINT,而是每帧自己画:**

```
while (Running)
├─ while (PeekMessage(&Msg, 0, 0, 0, PM_REMOVE))   ← 先把队列排空
│     ├─ 收到 WM_QUIT → Running = false
│     └─ TranslateMessage / DispatchMessage → WindowProc
├─ RenderWeirdGradient(XOffset, YOffset)          ← 往 BitmapMemory 写像素
├─ GetDC → StretchDIBits → ReleaseDC              ← blit 到窗口
└─ ++XOffset                                      ← 于是画面动起来了
```
