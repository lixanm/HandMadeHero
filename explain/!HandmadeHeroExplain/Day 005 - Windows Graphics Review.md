## 二、开场:三封邮件的更正(前 20 分钟)

### 1. OBS 不用买采集卡了

Day 4 结尾他说"测不了性能,因为 OBS 桌面捕获把机器拖到接近 0 帧,得买采集卡"。观众写信告诉他:把 OBS 从**显示器采集**换成**"游戏采集"但这个'游戏'选整个显示器**,就一切正常了。他实测后确认有效 —— 省下一张采集卡(而且采集卡本身还有一堆坑)。

### 2. `CS_HREDRAW` / `CS_VREDRAW` **要留着**(Day 2 Q&A 的更正)

Day 2 Q&A 里他把窗口类样式整个删掉过(`CS_HREDRAW | CS_VREDRAW | CS_OWNDC` 全不要)。观众 Martin Vladek 写信来**实测**后指出:`CS_HREDRAW` / `CS_VREDRAW` 该留着。

| 样式 | 真正的意思 |
|---|---|
| `CS_HREDRAW` | 窗口**横向**改变尺寸时,**重画整个窗口**,而不是只画新露出来的那块 |
| `CS_VREDRAW` | 同上,纵向 |

**为什么现在需要它**:因为我们**要把位图拉伸到窗口尺寸** —— 窗口一变宽,整张图的缩放比例就变了,所以**必须整窗重画**,只补新露出的那条边是不够的。

> 他顺手把 `CS_OWNDC` 的事也定了:那个**现在仍然不需要**(但 Q&A 里解释了它到底干什么,见第七节)。

### 3. 小结构体改**按值传** —— 顺便讲透"指针别名"

他承认 `Win32UpdateWindow` 收了 `RECT *`(指针)而那个 `RECT` 是 `WM_PAINT` 里的**栈上局部变量**,这是老习惯(结构大就传指针)。观众指出:**能按值传就按值传**。

理由(他讲得很细):如果编译器看到的是 `RECT Rect`(整份传进来),它就可以假设

- 这是**我私有的副本**,别人不会再碰它;
- 不会和别的指针**指向同一块内存**(没有 **aliasing**)。

**什么是指针别名(pointer aliasing)**:两个指针**可能指向同一块内存**,而编译器不知道。

```c
*a = 5;
int y = *b;   // 如果 a 和 b 指向同一个地方,y 应该是 5!
```

看起来"`*b` 读两次,值肯定一样,合并成一次读就行" —— **编译器不敢**。因为 `*a = 5` 可能正好改掉了 `b` 指的地方。它没法证明 `a != b`,所以只能老老实实读两次。

**这跟"传指针给栈上变量"有什么关系**:只要参数是**指针**,编译器就必须假设"外面任何人、任何时候都可能通过别的指针改掉它指向的东西";而**按值传**等于当场告诉它"这个值我交给你了,里面的代码**不可能拿到它的地址**,所以它不会被改"。

> [!warning]
> 他反复声明自己**不是编译器作者**,这个例子只是"讲清楚方向";想听真的,去看 **Chandler Carruth**(LLVM 的优化作者)的讲座 —— 这一点后面 Q&A 又提了一次。

**结论(当天的改动)**:小结构体(`RECT`、`win32_window_dimension`)一律**按值传**。他还说,过去按值传大结构会吃亏,但**现在编译器足够聪明**,这条老经验已经该翻篇了。

## 三、`MSG` 该声明在哪儿?—— 作用域、栈、以及 C++ 的不同

有观众写信说:跟着敲的时候,不小心把 `MSG Message;` 声明到 `while` 循环**外面**了,机器码上有区别吗?

**他的回答:基本没有区别。**

| 概念 | 说明 |
|---|---|
| **栈(stack)** | 程序运行时**预留给我们的那块内存**,函数调用时长大、返回时缩小 |
| 局部变量的"分配" | 不是真分配,只是**把栈顶往外挪一点**,给这个变量腾地方 |
| 他的比喻 | 像**游泳池的水位**:涨上来、退下去,用的**永远是同一块空间**,反复复用 |
| 声明写在哪儿 | 编译器**在它愿意的时候**(通常在函数序言里)一次性把栈挪够 —— 写在循环里不会让栈"每圈涨缩一次" |
| 那为什么还要写进循环里 | **纯粹为了你自己**:写进 `while` 里,循环外面的人就**引用不到**它。这叫**词法作用域(lexical scoping)**尽量收窄 |

**为什么要收窄作用域**(他的理由很实际):代码经常被搬来搬去、剪切粘贴,一个变量如果作用域很宽,搬动时就容易"不小心还留着它"→ 出 bug。收窄了,**编译器能帮你抓几个错**。他还给了一个排查全局变量的小技巧:在干净编译的程序里,给某个变量名**末尾随便加个字符**再编译,所有引用它的地方都会报错 —— 就等于"全局搜索"。

### ⚠️ 但 C++ 里**有真正的区别**:构造函数 / 析构函数

| | C | C++ |
|---|---|---|
| 把对象声明在循环里 | 只影响作用域(编译期的事) | 如果它有**构造/析构函数**,那么**每圈循环都要调用一次构造、出作用域调用一次析构** |
| 谁负责 | 编译器随便安排 | **标准强制要求**,编译器**没有自由度**去省掉它 |

这就是**真实的程序行为、甚至可能是性能差异**(构造可能是昂贵操作)。我们这条系列**几乎不会用这种东西**,但用 C++ 写代码的人必须知道。

> 他还解释了 `WNDCLASS WindowClass = {0};` 这一步:大括号里什么都不写 = 让编译器**清零**。他在调试器里给大家看了 `WindowClass` 在栈上的地址和清零前后的内存。

### Emacs 小贴士

他 `init.el` 里用的字体是 **Liberation Mono**,那不是系统自带的;想直接套用他的配置就得自己去(Red Hat 那个页面)下载 —— 他不能把字体打包进去,**因为他希望这个系列的所有东西都是公共领域可分发的**。

## 四、★ 重构一:全局变量打包成"离屏缓冲"结构体

### 1. 他不喜欢全局变量

理由不是性能,是**可读性**:全局变量"谁、什么时候、在哪儿改的"很难看清。他想让**任何读这份代码的人一眼看懂:"屏幕上那张图,要存在需要哪些东西"**。

于是他开了一个结构体,把 Day 3/4 的五个全局变量收进去:

```c
struct win32_offscreen_buffer
{
    BITMAPINFO Info;      // 这块位图的"说明书"(给 StretchDIBits 看)
    void      *Memory;    // 像素内存(我们 VirtualAlloc 出来的)
    int        Width;
    int        Height;
    int        Pitch;     // 一行多少字节 = Width * BytesPerPixel
    int        BytesPerPixel;
};

global_variable win32_offscreen_buffer GlobalBackBuffer;   // 全局还是留了一个,但只剩这一个
```

> 命名:因为已经在结构体里了,字段名不用再带 `Bitmap` 前缀(`Width` 而不是 `BitmapWidth`)。
> 结构体名字暂时叫 `win32_offscreen_buffer` —— 他明说"因为我没想到更好的名字"。

### 2. 三个函数全部改签名(以及**为什么有的按值、有的按指针**)

| 函数 | 新签名 | 传法 | 为什么 |
|---|---|---|---|
| `Win32ResizeDIBSection` | `(win32_offscreen_buffer *Buffer, int Width, int Height)` | **指针** | 它要**改**这个 buffer(填尺寸、改 Info、换内存)—— 按值传的话,**改动全都会消失在副本里** |
| `RenderWeirdGradient` | `(win32_offscreen_buffer Buffer, int XOffset, int YOffset)` | **按值** | 它只**读**这份数据(真正写的是 `Buffer.Memory` 指向的内存,那是个指针,副本里也照样指到) |
| `Win32DisplayBufferInWindow` | `(HDC, int WindowWidth, int WindowHeight, win32_offscreen_buffer Buffer, int X, int Y, int W, int H)` | **按值** | 同上,只读 |

**关于"改 buffer"的两种做法**(他专门停下来讨论):

| 做法 | 说明 | 他的评价 |
|---|---|---|
| 函数式:按值传 + **`return` 一个新的 buffer** | 调用方必须**接住返回值** | "a little bit error prone"(容易漏接),不推荐 |
| 就地修改:传**指针**,直接改原对象 | 调用方不用管返回值 | ✅ 他选这个 |
| 代价 | 指针 → 编译器又没法排除 aliasing | 无所谓:这个函数**只在窗口改变大小时调一次**,不在每帧的热路径上 |

> 他还调侃:真希望 **Chandler Carruth** 在看直播,好告诉他"这么写到底有多蠢"。

### 3. 改名字:`Win32UpdateWindow` → `Win32DisplayBufferInWindow`

因为它的本质就是"**把缓冲显示到窗口里**"。他顺手强调了命名约定:**平台层的函数一律带 `win32` 前缀**(`UpdateWindow` 是 Windows 自己的 API,撞名会编译不过)。他还说:如果你跟着敲,**名字随你起,别被我洗脑**。

### 4. `GlobalBackBuffer` 是故意的"临时妥协"

他没有把全局变量彻底消灭,而是**只留一个全局的 buffer**。理由:

> **如果某个"更干净"的改法在概念上漂亮、但实际换不来任何好处,那就是纯粹的浪费时间** ——
> 而写代码的目标是"**用最少的程序员时间,产出没有 bug 的、性能也够快的代码**"。

这个观点值得单独记一句,因为它是他整条系列里反复出现的价值观。

## 五、★ 现场崩溃:写地址 `0x00000000`(本集名场面)

重构完,一按 F5:

```
Access violation writing location 0x00000000
```

他说:**"这是我们的第一个访问违例。"** 但他**没有立刻去修**,而是先把这件事讲清楚。

### 1. 访问违例到底发生了什么

| 步骤 | 说明 |
|---|---|
| 程序里默认**没有任何**保留/提交的页 | Day 4 讲过:虚拟内存要 `VirtualAlloc` 才有 |
| 一旦碰了**无效页** | CPU 报警 → 交给操作系统 → 操作系统说"你在碰一块我不认的内存" |
| 于是**程序被终止** | Linux 上叫 segmentation fault / SIGSEGV,Windows 上他也说不清官方叫法,总之弹这个框 |
| **注意:不是所有这种异常都是 bug** | 你 `MEM_RESERVE` 过的页,第一次写时操作系统会**替你提交物理内存**,那种异常是正常的、会被悄悄处理掉 |

### 2. 崩溃原因(一句话)

答案就在报错框里那个指针:

```
Access violation writing location 00000000
                                    ↑ 指针是 0
```

**我们往一个从未初始化的指针里写东西。**

顺藤摸瓜:

1. `Pixel` 是 0 → `Row` 是 0 → `Buffer->Memory` 是 0;
2. 走进 `Win32ResizeDIBSection`,看到 `BitmapMemorySize` 算出来是 **0**;
3. 因为 **`BytesPerPixel` 从全局变量搬进结构体之后,他忘了给它赋值**;
4. 于是 `宽 × 高 × 每像素字节数` = `宽 × 高 × 0` = **0**;
5. `VirtualAlloc(0, 0, ...)` —— **要 0 字节,就给你 0 字节**,返回指针 0;
6. 渲染时往 0 写 → 崩。

> 一句话:**"像素不需要内存来存没有大小的东西。"**

### 3. 他借这个机会讲的"断言"哲学(重要)

他承认:**如果代码里有断言,这个错当场就会被抓住。** 但他把错误分成两类:

| 类型 | 特征 | 要不要担心 |
|---|---|---|
| **每次运行都出** | 你一跑就崩、就报错 | ❌ **不用怕**。你**绝不可能**把它发到用户手里,因为它太显眼了 |
| **偶发/潜伏** | 只在特定条件下出现,可能在你**发布之后**才出现 | ✅ **这才是真正要怕的** |

所以:"不是抓住所有错误都那么重要" —— 重要的是抓住**第二类**。断言当然会写,但**不是现在**(他说大约 2~3 周后专门讲)。这个错属于第一类,所以"其实不太需要防"。

## 六、★ 重构二:固定分辨率后备缓冲 + 真正开始拉伸

### 1. 改动本身

| 改之前(Day 4) | 改之后(Day 5) |
|---|---|
| `WM_SIZE` 里每次都重建后备缓冲,**缓冲尺寸 = 客户区尺寸** | 启动时**只建一次**,固定 **1280 × 720** |
| blit 是**1:1** 拷贝(两边尺寸相同) | blit 把 1280×720 **拉伸**到窗口尺寸 |
| 所以窗口一 resize 就重新分配内存 | 缓冲**一直活着**,由我们不断更新 |

```c
/* 启动时,进消息循环之前: */
Win32ResizeDIBSection(&GlobalBackBuffer, 1280, 720);
```

**为什么这么做**(这一步很关键,是整个系列的路线):

- 游戏**必须**用**固定分辨率**渲染 —— 否则换个屏幕尺寸,你的视野、碰撞、UI 布局全变;
- `StretchDIBits` 的**源矩形**从此永远是 `0,0,1280,720`,**目标矩形**才是当前窗口大小 ——
  这正是 Day 3 选 `StretchDIBits`(而不是 `BitBlt`)的原因,今天兑现了。

### 2. 于是抓到一个**潜伏了很久的 bug**:参数写反了

改完一跑,画面**完全错乱**。他的第一反应是"我们读过手册,但显然忽略了它":

| `StretchDIBits` 的参数顺序 | 我们填的 | 应该是什么 |
|---|---|---|
| 第 2~5 个 = **目标**(画到窗口哪里) | ~~缓冲尺寸~~ | **窗口尺寸** |
| 第 6~9 个 = **源**(从缓冲哪里取) | ~~窗口尺寸~~ | **缓冲尺寸** |

**为什么以前没暴露**:因为改之前**两边尺寸完全一样**(缓冲就是按客户区建的),写反了照样能显示 —— **这个 bug 一直躺在那里,只是看不出来**。

> [!tip]
> **这条直接关系到我们**:我们现在传的 `0,0,WindowWidth,WindowHeight` / `0,0,BitmapWidth,BitmapHeight` 是对的,
> 但一旦后备缓冲改成固定分辨率,**写反就立刻完蛋**。我们代码里已经有一段警示注释,可以放心。

### 3. 新的问题:**拉伸质量很差**

拉伸能用了,但他指出:**"这不是一次好的拉伸。"** 它是"最近邻"式的,不做任何**过滤(filtering)**,放大后会有明显的锯齿/方块感。

| 待办 | 说明 |
|---|---|
| 拉伸模式 | Q&A 里有人提 `SetStretchBltMode` + `HALFTONE` 能改善;他说"以后再看" |
| 过滤 | **他真正想要的是过滤** —— "`StretchDIBits` 可能不够工业强度",**不排除自己写过滤代码** |
| 宽高比 | **留了 TODO**。现在窗口一拉长,画面就被压扁/抻长("小 handmade hero 会被横向压扁或纵向抻长")。他说这事**要在某集开头专门花时间做对**,而且**可能用浮点、也可能用整数,还没想好**(时间不够,决定不了) |

## 七、★ 调试器里把整份代码走一遍(47:30 ~ 1:24:00)

### 1. 栈实验:栈往哪边长?有多大?

| 步骤 | 结果 |
|---|---|
| 在 `WinMain` 第一行下断点看到:进入我们代码之前,CRT 已经跑了一堆东西 | 他说"想完全绕开 CRT 也行,但要等胆子大的时候" |
| 看 `WNDCLASS` 的栈地址(如 `2CF5F0`),看参数 `hInstance` 等紧挨着排 | 确认这些**都在栈上** |
| 想知道"栈往高地址长还是低地址长" | 比较外层函数的局部变量地址(`1FFCA0`)和更内层函数的(`1FFBF0`)→ **数字变小了** |
| **结论** | **栈向低地址增长**(每压一样东西,地址更低) |
| 由此推出的推论 | 局部变量地址离 0 大约只有 1~2 MB,而 0 是空指针、越界会崩 → **栈最多也就这么大** |
| 实验:在栈上开 **2 MB** 的数组 | ⚠️ 第一次居然"通过了" —— 因为被**优化掉了**;让它真的被用上,立刻 **stack overflow** |
| 二分逼近 | 2 MB 崩 → 1 MB 附近开始不稳 → 到某个值时报的是 **"unhandled exception during user callback"**(栈刚好够自己活着,但一调进 Windows 就爆) |
| **结论** | 进入我们第一个函数时,手上大概**只有约 1 MB 栈**(Windows 链接器的默认值就是 1 MB) |
| 顺带找到控制开关 | cl 的 **`/F`(Stack size,`/Fnum`)**。他现场在 `build.bat` 里加了 `-F4194304`(4 MB),**验证确实生效**,然后**删掉了** |

**他为什么要费这个劲**(这是重点,不是炫技):

> **内存不是免费的,不是有个"内存小精灵"往你身上撒内存粉。**
> 连"编译器 + Windows 替你管着"的栈,也只有固定那么多。
> 每次调用函数你都得知道**自己吃掉了多少栈**。
> 尤其是以后要写**递归**函数(比如射线投射之类)—— 每次递归哪怕只用 10~50 KB,40 层就是 0.5 MB 起步,而总量不到 2 MB。

> [!tip]
> **对我们的意义**:我们这份代码目前栈用得极少,不用改 `build.bat`。但**"有个 `/F` 开关、默认约 1 MB"这件事值得记住** ——
> 以后写递归渲染(光照那一段一定会)时,这是第一个要想到的地方。

### 2. 逐行走代码时讲清的点(挑值得记的)

| 位置 | 他讲了什么 |
|---|---|
| **`hInstance` 到底是干嘛的** | **一个指针只在"它所属进程的地址空间"里唯一**。Windows 回调你要靠"函数地址",但光有地址它不知道是**哪个进程**的地址空间 → 所以要靠 `hInstance` 说明"按这个进程的地址空间解释这个指针" |
| **`RegisterClass(&WindowClass)` 传的是栈上变量的地址,安全吗** | **安全**:Windows 会**自己拷一份**读走,不依赖我们那份。但他提醒:**不是所有 API 都这样** —— 有些传进去的地址要求"你得让它一直活着",用之前要看文档 |
| `WS_OVERLAPPEDWINDOW` | 就是一个 **32 位位域**,一堆 bit 拼起来的"复合样式"(标题栏、关闭按钮、可缩放边框……) |
| **`CreateWindowEx` 里的 `hInstance`** | 他觉得这两个参数"有点过时"(Windows 本来就知道是谁在调),但传了不会错 |
| **`PeekMessage` 三个 0** | 不过滤:**任何窗口**的消息、**任何范围**的消息都要 |
| **`PM_REMOVE`** | 取走(而不是只瞄一眼) |
| **为什么要自己查 `WM_QUIT`** | 因为换了 `PeekMessage`,就**没有** "GetMessage 返回 0 = 该退出"那个信号了 |
| **`TranslateMessage`** | 把按键消息翻译成字符消息(他坦白:"我不确定我们有多在乎它,但这是常规做法") |
| **⚠️ Windows 可以**随时**回调你** | **不一定**只在 `DispatchMessage` 期间 —— 所以"任何一次调用 Windows 的 API,它都可能顺手回调进你的 `WindowProc`" |
| **`RenderWeirdGradient` 里 `Row` 必须是 `uint8 *`** | 因为 `Pitch` 的单位是**字节**(算它的时候乘了 `BytesPerPixel`)。如果 `Row` 是 `uint32 *`,C 会**悄悄再乘 4** → 一次跳 4 行 |
| **`*Pixel++` 的两层意思** | ① `*Pixel` = 写"指针指向的那个格子";② `++` 是**后置自增**,本语句执行完再前进一格。而且因为类型是 `uint32 *`,编译器**悄悄 +4 字节** = 正好一个像素 |
| **打包那行** | 寄存器里是 `XX RR GG BB`,内存里是 `BB GG RR XX` —— **小端**替我们做了反转。蓝放最低 8 位、绿左移 8 位,红和填充留 0 |
| **`GetDC` / `ReleaseDC`** | 是"**借**"和"**还**",必须成对。DC 本质是 Windows 的**状态容器**(笔、刷、裁剪区……),我们其实不需要这些,但走这条路就得过它 |
| **`EndPaint` 就够了,不用 `ValidateRect`** | 有观众照文档问"是不是还得 `ValidateRect`" → **不用**:`EndPaint` **隐式**把脏区域标记为已重画 |
| **脏区域(validation)是什么** | Windows 记得"你窗口上哪块需要重画"(比如被别的窗口挡住又露出来)。它发 `WM_PAINT` 给你,**等你告诉它画完了**;如果你**一直不说**,它会**一直发** `WM_PAINT` → **把你的消息队列刷爆** |
| **`DefWindowProc`** | 没处理的消息交给它 —— 它是个"兜底",会按默认行为处理 |
| **我们现在是个"嗑了药的吉娃娃"** | 消息排空 → blit → 再排空 → 再 blit,**占满一个 CPU 核**。他说现在没关系,以后会加计时 + `Sleep` |
| **调试期的一个坑** | 程序还在调试器里跑着时**没法重新编译**:Windows 会报 `cannot open win32_handmade.exe for writing`。**先 Shift+F5 停掉**。他说 Linux 用 inode + 引用计数,不会有这个问题;Mac 大概也是(他不确定) |
| **他真情流露的一段** | "观众写信说玩这个缓冲玩得很开心,我特别高兴 —— **这才是编程的快乐**:你和 CPU 之间没有 80 万个库、没有链接错误、没有上 Stack Overflow 找一个能让它工作的编译开关。就一个简单的构建脚本,一切都在你手里。像当年打开 Apple II 敲 BASIC 那样。" |

### 关于 aliasing 的那一大段(值得单独记)

这次他讲得比白天更完整,而且**翻了车又爬回来**(他自己吐槽"这应该是个 5 分钟就能写完的例子,我用了 15 分钟"):

| 要点 | 说明 |
|---|---|
| **"别名"这个词有很多种** | **缓存别名(cache aliasing)**、**TLB 别名**……那些是 **CPU 性能问题**;今天讲的**指针别名**是**语言/编译器问题**,跟 CPU 无关 |
| 本质 | **两个指针可能指向同一块内存,而编译器不知道** → 所以它**不敢**消除"看起来重复"的读 |
| 最小的例子(他终于写对了) | 读 `*B` → 写 `*A` → 读 `*B` → 写 `*C`。编译器想"把 `*B` 读一次、写两次",但**中间那个写 `*D` 可能正好写到 `B` 指的地方**(如果 `B` 和 `D` 别名),所以**必须重新读** |
| **只有写才会出问题** | 如果你只是**读**这些指针,通常没事 —— 是"写"创造了"别人可能改掉它"的可能性 |
| 多线程 | `volatile` 就是用来告诉编译器"**别的线程可能改这块内存**"的 |
| 观众补充(他确认正确) | **编译器被允许假设"两个指向不同类型(除 `char` / `unsigned char` 外)的指针永不算别名"** |
| 他的态度 | 现在编译器**越来越爱假设"没有别名"**,而他认为**这是"等着发生的 bug"** —— 连 RAD 都默认把这个模式关掉了。他更希望**反过来**:默认假设有别名,**你想优化时自己去标"这里没有别名"**(`restrict`、`__assume` 之类),可惜语言支持得很零碎 |
| 想深入 | 去看 **Chandler Carruth** 的讲座(LLVM 优化),"他会告诉你优化器里到底发生了什么" |
